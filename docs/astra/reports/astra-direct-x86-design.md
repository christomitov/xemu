Unexpected do_init0 on the retained-bank entry traps rather than replaying/reinitializing an unproven continuation. Original B bodies remain typed separately in the module.
- Active function uses legacy dispatch scaffolding with a separately typed, biased architectural bank; initializes once per fresh entry. Reference PC uses original independently captured slot target, or canonical env.eip for PCREL/other exit; expected Jcc slot is also checked independently, including equal-PC arms.

**Goal:** improve generated guest code, not C-module size. Opt-in, game-independent second backend; TCG remains the reference and fallback. Staged implementation received GO after measured class-time attribution; each extension retains its own correctness gate.

## 1. Translation and eligibility

Keep cold TCI/TCG execution initially. Capture bounded instruction bytes and instruction boundaries during the existing translation fetches—never reread guest code speculatively or duplicate instruction-fetch MMIO. At the existing hot-compilation point, decode those bytes into x86 operations and emit Wasm directly, without consuming TCG IR or TCI operations. Cold translation still builds TCG in this first cut; this is not initially a translation-time optimization.

Admission is whole-TB, before execution. Any unsupported instruction, ambiguous prefix, mode or resource limit selects the original backend. Begin with audited 32-bit protected-mode integer register operations, arithmetic/logic, comparisons, shifts, addressing and branches; add scalar RAM loads/stores and stack/call/return operations only with their precise commit rules implemented. Admit flat-segment assumptions only through sufficient live/TB-state guards. Initially reject LOCK/REP, unusual segmentation/address sizes, privileged/system operations, x87/MMX/SSE, plugins, debugging/single-step and parallel execution. SIMD/FPU are subsequent coverage milestones, not accidental scalar emulation.

## 2. Architectural state

Use architectural i32 GPR locals, dirty/valid masks and an exact lazy-flags packet. Preserve QEMU's flag semantics, including partial registers, preserved flags, zero-count shifts and its policy for architecturally undefined flags. Compute only flags actually read; export the standard QEMU lazy-CC representation or materialize flags when required by an architectural boundary.

Initially flush dirty state at TB exits. The performance milestone is **direct-only regions** retaining architectural locals between members. Keep every existing member-entry IRQ/icount, can_do_io and ownership/generation check. Spill before any taken exit or helper that can observe state; invalidate caches after helpers. No backedge-only polling or altered clocks.

## 3. Existing ABI, coexistence and lifetime

Preserve `start(WasmContext *) -> uintptr_t`, the current TB identity/header, dispatcher return conventions and IC2 policy. Publish through existing instance ownership, relinking and invalidation; clear incoming/outgoing links before function-index reuse. Retain the TCG fallback and bounded decode/restore metadata under that same TB lifetime.

Direct code needs a **versioned blueprint/local-layout descriptor**: the region merger currently assumes TCG's register globals and local numbering. Do not copy incompatible bodies into it. First use homogeneous direct regions and unchanged TCG regions; transitions between them flush/reload through the ordinary architectural ABI. Mixed-region fusion is later work.

## 4. Memory, faults and Asyncify: mandatory correctness gate

Reuse the existing live TLB tag, alignment, span, MMU and addend checks. Only a proven ordinary-RAM hit accesses memory inline. NOTDIRTY, GPU/watch callbacks, MMIO and other declines use the unchanged slow helpers and dirty/SMC machinery. No notdirty optimization is bundled.

Before a faultable/suspending path, publish exactly the state committed before that guest instruction. Commit its destination/flags/stack changes only at the architecturally correct point. **TCG return PCs and restore metadata cannot blindly be reused:** their lazy-CC metadata and temporary allocation may disagree with direct code. Establish an explicit direct fault-site/restore-map contract covering guest PC, committed CC state and instruction accounting, with valid lifetime-bound GETPC sites and selection distinct from legacy restoration. This must pass precise-fault tests before memory instructions are admitted.

Provide fresh-entry and rewind bodies under the existing `do_init`/`rewind_func` protocol, with a layout-aware snapshot of live continuation state. Rewind resumes the suspended helper without repeating completed instructions or stores. Keep the one-suspended-activation-per-module restriction. No mid-TB restart into original TCG after a prefix has executed.

## 5. Validation and expected gain

Differentially execute **real captured guest blocks** through the existing TCG-generated Wasm and the new backend in isolated architectural/RAM fixtures. ### Expected benefit: conditional planning model, not a measured forecast

Historical context only, not the current baseline: the earlier supplied SC profile was ~75% JIT, ~12% dispatch, ~3.4% RDTSC at ~27 FPS. On the assumption that the vCPU is the critical path, let `f` be the **actual productive eligible fraction of JIT time**, and `r` the fraction of that eligible time removed. Ignoring added overhead, overall speedup is `1 / (1 - 0.75*f*r)`.

A planning target of **20–30% less eligible native-code time**, if eligible code accounts for **25–45% of JIT time**, gives about **+4–11% SC**, or **28.1–30.0 FPS from 27**. At that point neither `f` nor `r` was measured; those were scenario assumptions, NOT the 45.48% instruction-weight census substituted into a time model. Reaching 30 from 27 requires `f*r >= 0.1333` at JIT=75%, before overhead. Reaching comfortably above 30 may need broader FPU coverage and/or the coordinator's separate dispatch work.

The numerical scenario above is historical, not a forecast for the clean ~28.5 FPS baseline. Use the new capture's overall eligible nonself share `p`, rather than retaining the old 75% JIT fraction. Conditional speedup is `1 / (1 - p*r)`; 28.5→30 would require removing 5% of total critical-path time before added overhead. Neither productivity nor removal fraction `r` is measured by this profiler. Rebase again when accepted link/NOTDIRTY changes ship: JIT fractions and costs will change. Do not add the coordinator's dispatch percentage to this estimate or count it as translator savings. A single-TB stage can be neutral; the performance target is the memory-capable, homogeneous-region milestone.

There is no defensible GR FPS estimate without its current critical-path/class-time fractions. R6 walk is already ~29.8 FPS in this capture; target headroom and fewer dips, not an uncapped FPS extrapolation. Its two hottest captured headers share PC `43bb610` and together account for 31.70% of pointer samples; their five instructions form a repeated memory-load/compare/backedge polling-shaped loop. The same byte pattern appears in GR at `43790b0`. This is evidence that huge integer counts can include waiting, NOT proof of productive time. Keep every load and interrupt check; never short-circuit or batch the poll.

The hot snapshots contain only 24 headers, cover 15.92% / 26.42% / 61.89% of pointer samples, and are not phase-conditioned (the census captures have no vCPU phase samples). Some guest bytes are truncated at 256 bytes. They cannot establish a full JIT-time ranking.
